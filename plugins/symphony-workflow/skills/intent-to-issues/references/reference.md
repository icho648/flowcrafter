# Intent 到 Issues — GitHub 写入与恢复流程

本文件只在 canonical `SKILL.md` 的结构确认和“是否推送到 GitHub Issues？”得到明确肯定后
读取。没有明确确认时，只输出草案，不执行外部写入。

## 写入前检查

1. 检查目标仓库、当前权限、重复 Issue，以及 GitHub 当前可用的父子关系能力。
2. 先确认最终的 Parent / Sub-issues 结构没有变化；如果用户改变了目标、范围、验收、依赖、
   责任或写入授权，回到 canonical 工作流重新确认。
3. 确认将要创建的最小条目数量、父子关系和依赖顺序。

## 创建顺序

1. 先创建或确认 Parent。
2. 再按依赖创建 Sub-issues，并使用 GitHub 原生关系链接。
3. 如果当前工具或仓库不支持原生父子关系，先说明限制，不伪造关系。

## 写入边界

- 不擅自修改状态、标签、负责人、里程碑、权限、Commit、Merge 或 Close；这些是独立决定，
  除非用户明确授权。
- 只写入已确认的目标、范围、验收、约束、依赖、非目标和证据字段。
- 不把实现类、文件、命令和任务顺序写成产品契约，除非它们是已确认的安全、协议、兼容或
  迁移约束。

## 结果与恢复

1. 记录返回的 Issue ID、URL、父子关系和失败项。
2. 创建部分成功时停止，不盲目重试，先报告已完成项、失败项和可恢复动作。
3. 重新读取 Parent、Sub-issues 和关键关系，确认没有重复、孤儿或错误链接。
4. 没有可用写入工具时，只返回可直接复制的 GitHub Issues 草案，不声称已经创建。

在当前仓库的 `Not verified` 阶段，文档演练、Mock 或 Agent 自述不能当作真实 GitHub
Issues 创建或运行证据。
