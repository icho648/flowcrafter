# Intent 到 Issues

先判断是否需要拆解，再决定如何表达和是否写入 Tracker。默认是一条 Issue；拆解只为表达
真实的交付边界，不为制造更多条目。

## 启用前检查

1. 确认当前请求包含 $intent-to-issues、/symphony-workflow:intent-to-issues 或
   /intent-to-issues。
2. 如果没有显式调用，不启用本技能，也不要把普通规划、项目管理或 Issue 关键词当作隐式调用。

## 1. 建立最小理解

- 读取当前工作区的指导文件、产品边界和相关规格；事实能从仓库或 Tracker 查到就先查，
  不要拿它当问题问人。
- 用一句话写出 Intent：谁要什么结果，以及为什么现在做。
- 区分事实、决策、假设、待定和建议。待定项若会改变目标、范围、验收、依赖、责任或
  外部写入授权，先停下来。
- 需要人决定时，一次只问一个最高影响问题，并给出推荐答案和影响。没有形成共同理解和
  最终结构确认前，不创建 Issue。

## 2. 拆解门槛

先问：同一责任人能否用一组清晰验收条件，在一个 Issue 中完成并交付这个 Intent？
如果能，保留单 Issue，改善它的目标、范围和验收；不要为了状态展示、估算、排期或
“看起来完整”而拆。

只有出现真实边界时才拆成 Parent + Sub-issues，例如：

- 子工作是可独立验收、Review、回滚或交接的交付物；
- 存在必须表达的先后依赖或明确的并行边界；
- 不同子工作需要不同责任人、权限、Workspace、风险控制或验收人；
- 父级需要保留集成、整体验收或人工决定，而子级分别产出证据。

不要因为任务描述很长、实现步骤很多、想显示进度、每个技术层都想有一条 Issue，或
子项无法脱离其他子项独立判断完成，就进行拆解。没有真实边界时，拆出来的只是
checklist，不是 Sub-issue。

## 3. 设计最小 Issue 树

Intent 是要达成的结果，不自动等于一个 Issue。Parent Issue 是目标、范围和集成责任的
协调边界；Sub-issue 是一个独立可验证的交付物，不是父级的命令清单。

- Parent 保留问题、目标结果、整体验收、共享约束、依赖关系和最终 Review / 集成责任。
- 每个 Sub-issue 只承载一个可交付结果，写清范围、验收条件、依赖、非目标和需要留下
  的证据。
- Siblings 不重叠；父子关系、阻塞关系和普通相关链接分别表达，不混用。
- 只创建达到交付边界所需的最少子项；默认不创建孙级树，也不为未来工作预留空 Issue。
- Parent 不应变成所有子项的垃圾桶。如果它没有独立的整体目标或集成责任，直接使用
  单 Issue 或重新定义边界。

草案只保留有用字段，通常包含：

- 问题 / Intent / 目标结果
- 范围内行为
- 验收条件
- 约束与依赖
- 非目标
- 需要留下的证据

不要把实现类、文件、命令和任务顺序写成产品契约，除非它们是已确认的安全、协议、
兼容或迁移约束。

## 4. 先确认结构，再考虑写入

先输出单 Issue 或 Parent + N 个 Sub-issues 的建议，并说明为什么这是最小有用结构。
拆解草案完成后，只问一个收口问题：

    是否推送到 GitHub Issues？

只有用户明确确认后，才进行外部写入。用户未回答、回答含糊或只确认了拆解方案时，
只返回草案，不创建或修改 Issue。

## 5. 写入 GitHub Issues

用户确认写入后：

1. 检查目标仓库、当前权限、重复 Issue，以及 GitHub 当前可用的父子关系能力。
2. 先创建或确认 Parent，再按依赖创建 Sub-issues，并使用 GitHub 原生关系链接。
   如果当前工具或仓库不支持原生父子关系，先说明限制，不伪造关系。
3. 不擅自修改状态、标签、负责人、里程碑、权限、Commit、Merge 或 Close；这些是独立
   决定，除非用户明确授权。
4. 记录返回的 Issue ID、URL、父子关系和失败项。创建部分成功时停止，不盲目重试，
   先报告可恢复动作。
5. 重新读取 Parent、Sub-issues 和关键关系，确认没有重复、孤儿或错误链接。
6. 没有可用写入工具时，只返回可直接复制的 GitHub Issues 草案，不声称已经创建。

## 6. 输出契约

保持短而可执行：

- 决定：保留单 Issue，或拆成 Parent + 子项。
- Intent：一句话说明结果、原因和责任边界。
- 证据状态：标出事实、决策、假设、待定、建议；外部创建证据不足时标记未验证。
- 理由：指出真实交付边界；若不拆，指出拆解没有增加什么能力。
- 草案：每个 Issue 的目标、范围、验收、依赖 / 非目标和证据。
- 待确认：最多一个当前最高影响的问题；拆解完成后询问是否推送到 GitHub Issues。
- 已写入时：列出 ID、URL、父子关系校验和未完成动作。

在当前仓库的 Not verified 阶段，文档演练、Mock 或 Agent 自述不能当作真实 GitHub
Issues 创建或运行证据。
